## 1. Problem & Confirmed Decisions

**The problem, in the stakeholder's terms:**
Users have no way to indicate when a task needs to be done by. Tasks with deadlines look identical to tasks without, so nothing surfaces urgency. Users are asked to see at a glance which tasks are late.

### 1a. Decisions given by the stakeholder

Unchanged from the question round. **None of these is reopened by this revision.**

| # | Question | Decision given |
|---|---|---|
| 1 | Deadline precision | **Date only.** No time-of-day component. |
| 3 | Overdue boundary | A task due 2026-08-05 becomes overdue at the **start of 2026-08-06**. The whole due day belongs to the user. |
| 4 | How lateness surfaces | **Inline marker on the task row** AND **overdue tasks pinned to the top**. A persistent count badge and a dedicated Overdue filter/view are **cut**. |
| 5 | Ordering resolution | **Pinned "Overdue" section above the normal list**; the normal list's own order is preserved inside it. |
| 6 | Completing a task after its deadline | **Neutral.** No "completed late" marker. Drops out of the overdue grouping. |
| 7 | Middle state ("due today" / "due soon") | **None.** Binary — only Overdue is marked. |
| 8 | Deadline optionality | **Optional**, editable at any time, **past dates allowed** (immediately overdue), and **clearable** once set. |
| 9 | Notifications | **None in v1.** Purely visual. Email/push explicitly out of scope. |
| 12 | Delivery vehicle | **~2-hour POC.** One complete working path; everything else stubbed and named as stubbed. |

## 2. Users

| User | What they need |
|---|---|
| **Task user** — anyone with the app open at `http://localhost:3000` | To record "this must be done by X" on a task, and to know within one second of the page rendering whether anything has slipped past its date. |

There is exactly one role, and it is not a design choice — F2 establishes that the application has no identity concept at all: no accounts, no owner field, no per-user filtering. Every client is the same anonymous actor against one shared list. There is therefore no assignee, recipient or approver role to specify. **This is observed, not inferred.**

The multi-client consequence is real and is specified in EC-15: if two browsers are open, one user's due date is immediately visible to the other on their next render.

## 3. Acceptance Criteria

All criteria assume system date **2026-08-01** unless stated, a running server on port `3000`, and a store freshly `reset()` (F12). Field name `due_date` is the `PROPOSED` value from OQ-2 — if that changes, every JSON key below changes with it.

### API

**AC-1 — `GET /tasks` returns `due_date` on every task, defaulting to `null`**
*Given* the store is empty,
*when* the client sends `POST /tasks` with `{"title": "Buy milk"}` and then `GET /tasks`,
*then* the response is `200` and the body is exactly `[{"id": 1, "title": "Buy milk", "completed": false, "due_date": null}]`.
The existing three keys are unchanged in name, type and value; `due_date` is additive.

**AC-2 — `POST /tasks` accepts an optional `due_date`**
*Given* the store is empty,
*when* the client sends `POST /tasks` with `{"title": "Renew passport", "due_date": "2026-08-05"}`,
*then* the response is `201` and the body is exactly `{"id": 1, "title": "Renew passport", "completed": false, "due_date": "2026-08-05"}`.

**AC-3 — `POST /tasks` rejects a malformed `due_date` and creates nothing**
*Given* the store is empty,
*when* the client sends `POST /tasks` with `{"title": "Renew passport", "due_date": "05/08/2026"}`,
*then* the response is `400` with body `{"error": "due_date must be a date in YYYY-MM-DD format"}`, and a subsequent `GET /tasks` returns `[]`.

**AC-4 — `PATCH` sets a due date without touching `completed`**
*Given* a task created by `POST /tasks {"title": "File tax return"}` (so `id` = 1, `completed` = `false`, `due_date` = `null`),
*when* the client sends `PATCH /tasks/1` with `{"due_date": "2026-07-30"}`,
*then* the response is `200` with body `{"id": 1, "title": "File tax return", "completed": false, "due_date": "2026-07-30"}`.
Specifically: `completed` is still `false` and `title` is unchanged.

**AC-5 — `PATCH` no longer un-completes a task when `completed` is absent** *(regression guard on F11)*
*Given* a task with `id` = 1 that has been set to `{"completed": true}`,
*when* the client sends `PATCH /tasks/1` with `{"due_date": "2026-09-01"}`,
*then* the response body has `"completed": true`.
Before this change the same request would have returned `"completed": false` (F11). This criterion exists to stop that regression being reintroduced.

**AC-6 — `PATCH` clears a due date with an explicit `null`**
*Given* a task with `id` = 1 and `due_date` = `"2026-07-30"`,
*when* the client sends `PATCH /tasks/1` with `{"due_date": null}`,
*then* the response is `200` with `"due_date": null`.

**AC-7 — `PATCH` with an empty body changes nothing**
*Given* a task `{"id": 1, "title": "Walk dog", "completed": true, "due_date": "2026-07-30"}`,
*when* the client sends `PATCH /tasks/1` with `{}`,
*then* the response is `200` and the body is byte-for-byte the same task — `completed` is still `true` and `due_date` is still `"2026-07-30"`.

**AC-8 — `PATCH` rejects a malformed `due_date` before looking the task up**
*Given* the store is empty (no task with `id` = 99 exists),
*when* the client sends `PATCH /tasks/99` with `{"due_date": "not-a-date"}`,
*then* the response is `400` with `{"error": "due_date must be a date in YYYY-MM-DD format"}` — **not** `404`. Body validation precedes lookup.

**AC-9 — Existing endpoints are untouched**
*Given* the two existing tests in `python/tests/test_tasks.py`,
*when* `pytest` runs after this change,
*then* both pass unmodified: `POST /tasks {"title": "Buy milk"}` still returns `201` with `title` = `"Buy milk"` and `completed` = `false`; `PATCH /tasks/<id> {"completed": true}` still returns `200` with `completed` = `true`.

### Frontend

**AC-10 — A future deadline renders as text with no late signal**
*Given* a task `{"id": 1, "title": "Renew passport", "completed": false, "due_date": "2026-08-05"}`,
*when* the page renders,
*then* the row appears in `<ul id="task-list">`, shows the text `Due Wed 5 Aug 2026`, has no `overdue` class, no `OVERDUE` badge, and no red border.

**AC-11 — A task with no deadline shows nothing at all**
*Given* a task `{"id": 2, "title": "Buy milk", "completed": false, "due_date": null}`,
*when* the page renders,
*then* the row shows the title, an empty date input, the checkbox and the Delete button — and **no** date text and **no** placeholder such as "No due date".

**AC-12 — A past deadline renders in the Overdue section**
*Given* a task `{"id": 3, "title": "File tax return", "completed": false, "due_date": "2026-07-30"}`,
*when* the page renders on 2026-08-01,
*then* the row appears in `<ul id="overdue-list">` (not `task-list`), the `<h2 id="overdue-heading">Overdue</h2>` is visible, and the row carries the `overdue` class, the text `OVERDUE`, the text `Due Thu 30 Jul 2026`, and a red left border.

**AC-13 — Boundary: due today is not late**
*Given* a task with `due_date` = `"2026-08-01"` and the browser's local date is 2026-08-01,
*when* the page renders,
*then* the row is in `task-list`, **not** `overdue-list`, and carries no `OVERDUE` badge.

**AC-14 — Boundary: due yesterday is late**
*Given* the same task with `due_date` = `"2026-08-01"` and the browser's local date is 2026-08-02,
*when* the page renders,
*then* the row is in `overdue-list` with the `OVERDUE` badge.

**AC-15 — Overdue tasks sort most-overdue-first; the main list keeps creation order**
*Given* four incomplete tasks created in id order — `id` 1 `due_date` `"2026-07-31"`, `id` 2 `due_date` `null`, `id` 3 `due_date` `"2026-07-28"`, `id` 4 `due_date` `"2026-09-15"`,
*when* the page renders on 2026-08-01,
*then* `overdue-list` contains, top to bottom, `id` 3 then `id` 1 (earlier `due_date` first), and `task-list` contains, top to bottom, `id` 2 then `id` 4 (ascending `id` — creation order, per F4 and Q5a).

**AC-16 — Completing an overdue task removes every late signal**
*Given* an overdue task `id` 3, `due_date` `"2026-07-30"`, sitting in `overdue-list`,
*when* the user ticks its checkbox,
*then* a `PATCH /tasks/3 {"completed": true}` is sent, and after the re-render the row is in `task-list` at its ascending-`id` position, with class `completed`, strikethrough title in `#888`, **no** `OVERDUE` badge, **no** red border and **no** "completed late" wording anywhere.

**AC-17 — Clearing the date from the row control returns the task to the main list**
*Given* an overdue task `id` 3, `due_date` `"2026-07-30"`, in `overdue-list`,
*when* the user empties that row's date input,
*then* `PATCH /tasks/3 {"due_date": null}` is sent, and after the re-render the row is in `task-list` at its ascending-`id` position with no date text and no badge.

**AC-18 — Empty Overdue section is not rendered at all**
*Given* five tasks of which none is overdue,
*when* the page renders,
*then* `<h2 id="overdue-heading">` and `<ul id="overdue-list">` are both hidden — no heading, no divider, no "nothing overdue" message occupies the top of the page.

**AC-19 — Date rendering is timezone-safe**
*Given* a task with `due_date` = `"2026-08-05"` and the browser is set to a negative-UTC-offset timezone (e.g. `America/Los_Angeles`),
*when* the page renders,
*then* the row reads `Due Wed 5 Aug 2026` — **not** `Due Tue 4 Aug 2026`. (`new Date("2026-08-05")` parses as UTC midnight and renders the previous day west of Greenwich; the implementation must construct the date from its parts — see §7.)

**AC-20 — Adding a task with a date in one step**
*Given* the add form,
*when* the user types `Renew passport`, picks `2026-08-05` in the form's date input and submits,
*then* `POST /tasks {"title": "Renew passport", "due_date": "2026-08-05"}` is sent, both inputs are cleared, and the new row renders in `task-list` showing `Due Wed 5 Aug 2026`.

## 4. Explicit Assumptions

Everything below I decided. Nobody told me any of it, and the code does not settle it. Anything the code *did* settle has been moved to §1b and is no longer listed here.

| # | Assumption | Why | Impact if wrong |
|---|---|---|---|
| **A1** | **Time semantics: "overdue" means the whole due day has ended in the *viewer's browser-local* calendar timezone.** The rule is `due_date < todayLocal` on `YYYY-MM-DD` strings. Due `2026-08-05` is overdue from the start of `2026-08-06` local. No UTC conversion, no server clock, no timezone configuration. | Q2 was left open by the stakeholder. Date-only deadlines compared against the viewer's own wall calendar is the only rule that never disagrees with what the user sees on their own calendar, and it costs zero configuration. | The list is shared by all clients (F2), so a user in Sydney and a user in London can see the same task differently for up to ~14 hours. It also becomes structurally wrong the moment anything server-side (notifications, a report) needs to know what is overdue, because the server has no "viewer timezone". **Also OQ-1 — must be re-decided before any server-side use.** |
| **A2** | **Overdue is computed on the client and is never a field in the API response.** `GET /tasks` returns stored fields only; no `overdue` boolean is added. | Grounded in the existing architecture: `list_tasks` returns the store verbatim (`routes/tasks.py:8-10`) and no endpoint has any clock-dependent behaviour. Adding a derived time-dependent field would make `GET /tasks` non-deterministic and would break the existing test style (F12), which asserts on exact response bodies. It is also the only way A1 can hold. | If a consumer other than this frontend ever needs overdue status, it must reimplement the rule. If the rule then diverges between consumers, two clients disagree about the same task. |
| **A3** | **`PATCH` becomes a true partial update, keyed on field *presence*, not truthiness.** `completed` is applied only if the key is present in the body; `due_date` is applied only if the key is present (with `null` meaning clear). | Required, not optional: without it, the frontend's date-only PATCH would carry `bool(None)` and silently un-complete the task (F11). Presence-keying is the only way to send one field without clobbering the other. | This **changes existing behaviour** of a live endpoint: `PATCH /tasks/1 {}` used to set `completed = false` and now leaves it unchanged. No existing test covers that path (F12), so nothing catches it — AC-5 and AC-7 exist specifically to pin the new behaviour. Any external caller relying on the old coercion breaks silently. |
| **A4** | **Red (`#c0392b`) is reserved exclusively for the overdue signal.** Completion continues to use strikethrough + `#888` and is never coloured red. | F7 establishes red is currently unused, so reserving it costs nothing today. Reserving one colour for one meaning is the entire mechanism behind "see at a glance". | If priority, labels or an error state are later added in red, the overdue signal stops being scannable and the stakeholder's core requirement regresses. Any future colour work must avoid the red family. |
| **A5** | **The row and form date controls are native `<input type="date">`.** No date library, no custom picker. | Its value is natively the `YYYY-MM-DD` string, identical to the storage format — zero parsing, zero formatting on input, and browser-native validation of impossible dates. Keeps `requirements.txt` (F13) and the dependency-free vanilla-JS frontend untouched. | Older or niche browsers fall back to a free-text field, where a user can type `05/08/2026` and receive the AC-3 400 error with no inline hint. Acceptable for a POC demoed on a current browser. |
| **A6** | **Server-side date validation uses only the standard library** — a `^\d{4}-\d{2}-\d{2}$` regex followed by `datetime.date.fromisoformat()`. No new dependency. | F13 shows a two-line `requirements.txt`; adding a dependency to a 2-hour POC is disproportionate. The regex is load-bearing because `date.fromisoformat` accepts additional formats (e.g. `"20260805"`) on newer Python versions, and the README specifies only "Python 3" with no minimum — so the regex removes the version dependence rather than assuming one. | Without the regex, the accepted input set silently varies with the Python version on the machine, and AC-3 would pass on one interpreter and fail on another. |

```python
def create_task(title, due_date=None):
```

### Partial update — the sentinel

`update_task(task_id, completed)` must become presence-aware. `None` cannot signal "not supplied" for `due_date`, because `None` is the meaningful value for *clear the date*. A module-level sentinel is required:

```python
_UNSET = object()

def update_task(task_id, completed=_UNSET, due_date=_UNSET):
    task = get_task(task_id)
    if task is None:
        return None
    if completed is not _UNSET:
        task["completed"] = completed
    if due_date is not _UNSET:
        task["due_date"] = due_date
    return task
```

The route supplies an argument only when the key is present in the request body. This is what makes AC-5 and AC-6 both true at once, and it is what retires F11.

### Validation — `python/routes/tasks.py`

Validation lives in the route, not the model, matching the existing separation of concerns (the title check is already at `routes/tasks.py:15-17` while the model stays dumb).

```
_DATE_RE = re.compile(r"^\d{4}-\d{2}-\d{2}$")

valid iff  value is None
        or (isinstance(value, str) and _DATE_RE.match(value) and date.fromisoformat(value) succeeds)
```

Both the regex and `fromisoformat` are required (A6): the regex pins the accepted shape independently of Python version, `fromisoformat` rejects impossible dates such as `"2026-02-30"`.

On failure: `400` with `{"error": "due_date must be a date in YYYY-MM-DD format"}` — matching the existing error shape (F9).

**Ordering of checks in `PATCH`:** validate the body first, then look the task up. A malformed date on a non-existent id returns `400`, not `404` (AC-8). Rationale: a malformed request is malformed regardless of what it targets.

### API contract after the change

| Method | Route | Request body | Success | Errors |
|---|---|---|---|---|
| `GET` | `/tasks` | — | `200` — array of task objects, each with all four fields | — |
| `POST` | `/tasks` | `{"title": str, "due_date": str \| null}` (`due_date` optional) | `201` — the created task | `400 {"error": "title is required"}`; `400 {"error": "due_date must be a date in YYYY-MM-DD format"}` |
| `PATCH` | `/tasks/<int:id>` | any subset of `{"completed": bool, "due_date": str \| null}` | `200` — the updated task | `400` (malformed `due_date`, checked first); `404 {"error": "task not found"}` |
| `DELETE` | `/tasks/<int:id>` | — | `204`, empty body | `404 {"error": "task not found"}` |

`GET`, `DELETE` and the `title` handling are behaviourally unchanged. The only behaviour change to an existing path is A3's presence-keying on `PATCH`.

### Derived state — client only (A2)

```js
todayLocal = local Y-M-D of new Date(), zero-padded      // e.g. "2026-08-01"
isOverdue(t) = t.due_date !== null
            && t.completed === false
            && t.due_date < todayLocal                    // lexical compare; ISO dates sort correctly
```

`due_date < todayLocal` and **not** `<=`: decision 3 gives the user the whole due day. Due `2026-08-05`, on `2026-08-05` the comparison is false (AC-13); on `2026-08-06` it is true (AC-14).

**Why computed, not stored:** a stored overdue flag is correct only at the instant it is written and goes stale at every midnight, requiring a scheduled job this app has no machinery for (F1, F8). One string comparison per row at render time is always correct.

### Date formatting — client only

```js
// MUST construct from parts. new Date("2026-08-05") parses as UTC midnight
// and renders 4 Aug west of Greenwich (AC-19).
const [y, m, d] = due.split('-').map(Number);
const dt = new Date(y, m - 1, d);
// fixed arrays, not toLocaleDateString — output must be identical in every browser locale
=> "Due Wed 5 Aug 2026"
```

### Ordering rules

| Section | Order | Basis |
|---|---|---|
| **Overdue** | `due_date` ascending (most overdue first). Tie-break: `id` ascending. | AC-15. `id` is creation order (F4). |
| **Main list** | `id` ascending — i.e. the server's list order, used as-is. | F4 + decision 5 ("existing order preserved"). The server already returns this order (`routes/tasks.py:8-10`), so no client sort is needed for this section. Due date does **not** affect position here. |
| Completed tasks | Always in the main list at their `id` position, struck through. They never enter the Overdue section regardless of `due_date`. | Decision 6 |

The client sorts **only** the overdue partition. The main list is rendered in the order the API returned it.

### Rules

1. A task is in the Overdue section **iff** `isOverdue(t)` is true. The inline marker (decision 4a) and the pinned section (decision 4b/5) are two renderings of the same single boolean — not two independent features and not two sorts.
2. Setting, changing or clearing `due_date` triggers a `PATCH` followed by `fetchTasks()`, re-rendering the section split (AC-17, AC-20) — consistent with the existing mutation pattern at `public/app.js:40`, `45`, `58`.
3. Ticking the checkbox makes `isOverdue` false by definition, so the late signal disappears with no separate "completed late" state (decision 6, AC-16).
4. Un-ticking may restore overdue (EC-9).
5. Past dates are accepted with no warning and take effect immediately (decision 8, AC-12).

## 9. Edge Cases

| # | Case | Specified behaviour |
|---|---|---|
| **EC-1** | `POST /tasks` with no `due_date` key | Task created with `due_date: null`. `201`. Existing behaviour preserved (AC-1). |
| **EC-2** | `POST /tasks` with `"due_date": null` explicitly | Identical to EC-1 — `null` is valid. `201`. |
| **EC-3** | `due_date` sent as a non-string (`{"due_date": 20260805}`, `{"due_date": true}`, `{"due_date": ["2026-08-05"]}`) | `400` `{"error": "due_date must be a date in YYYY-MM-DD format"}`. The validator requires `None` or `str`; everything else fails the type check before the regex. |
| **EC-4** | Well-formed but impossible date (`"2026-02-30"`, `"2026-13-01"`) | `400` with the same message. The regex passes; `date.fromisoformat` raises and is caught (A6). |
| **EC-5** | Absurd but valid date (`"1900-01-01"`, `"2999-12-31"`) | **Accepted** (`PROPOSED`, OQ-5). `1900-01-01` renders at the very top of the Overdue section; `2999-12-31` renders in the main list. |
| **EC-6** | **Boundary: due today.** `due_date` = `"2026-08-01"`, browser-local date `2026-08-01` | **Not overdue.** Main list, no badge (AC-13). The whole due day belongs to the user (decision 3). |
| **EC-7** | **Boundary: due yesterday.** `due_date` = `"2026-08-01"`, browser-local date `2026-08-02` | **Overdue.** Overdue section, badge shown (AC-14). |
| **EC-8** | Page left open across local midnight | The section split goes stale until the next render. F8 establishes there is no timer and none is added (OQ-3, §6 out of scope). Any add, toggle, delete or page refresh corrects it. **Not** a defect — a specified limitation. |
| **EC-9** | Overdue task completed, then un-completed | Complete → leaves Overdue, no late marker (AC-16). Un-complete → `PATCH {"completed": false}` returns it to Overdue with the badge. Fully reversible, no residue, because overdue is derived (§7). |
| **EC-10** | Due date cleared while the task sits in Overdue | `due_date: null` stored. Row returns to the main list at its **ascending-`id`** position — not to the top, not to the bottom (AC-17). |
| **EC-11** | Future date edited into the past, or the reverse, from the row control | Row re-homes between sections on the `fetchTasks()` that follows the `PATCH`. Both directions behave symmetrically. |
| **EC-12** | `PATCH` with `{"completed": true, "due_date": "2026-07-30"}` in one request | Both applied in a single call; `200` returns the task with both new values. |
| **EC-13** | `PATCH /tasks/1 {}` (empty body) or a body with no recognised keys | `200`, task returned **unchanged** (AC-7). This is a deliberate change from F11, where the same request set `completed = false`. |
| **EC-14** | Two overdue tasks with the identical `due_date` | Tie-broken by ascending `id` (§7). Order is stable across renders and never shuffles between refreshes. |
| **EC-15** | Two browsers open against the same server, one sets a due date | The second browser sees the change on its next `fetchTasks()` — i.e. after its own next mutation or a refresh, not live. Direct consequence of the single shared in-memory list (F1, F2). No conflict detection, last write wins. |
| **EC-16** | Server restarted | **All tasks are lost**, including every due date. The store is a module-level list re-initialised at import (F1). Explicitly out of scope to fix (§6). |
| **EC-17** | `PATCH` or `DELETE` on a non-integer id — `/tasks/abc` | Flask's `<int:task_id>` converter does not match, so the request 404s at the routing layer with Flask's **default HTML 404 page**, not the JSON `{"error": "task not found"}`. Existing behaviour (`routes/tasks.py:21`, `30`); unchanged by this work. |
| **EC-18** | `PATCH` a valid-format date onto a non-existent id — `/tasks/99 {"due_date": "2026-08-05"}` | `404` `{"error": "task not found"}`. Contrast AC-8: a **malformed** date on the same id returns `400`, because body validation runs first. |
| **EC-19** | Overdue task deleted | `DELETE /tasks/<id>` → `204`, unchanged behaviour. Row leaves the Overdue section; if it was the last one, heading and list become `hidden` again (AC-18). |
| **EC-20** | Request body is not JSON at all, or `Content-Type` is missing | `request.get_json(silent=True) or {}` yields `{}` (existing pattern, `routes/tasks.py:15`, `23`). `POST` → `400 title is required`; `PATCH` → `200`, unchanged task (EC-13). |
| **EC-21** | Whitespace-only title, e.g. `POST /tasks {"title": "   "}` | **Accepted** by the API and created with `due_date: null` — `" "` is truthy in Python (F10). The frontend still blocks it by trimming (`public/app.js:50-51`). Pre-existing behaviour, deliberately **not changed** by this feature. |
| **EC-22** | Browser in a negative-UTC-offset timezone renders a due date | Shows the stored calendar date, not the day before (AC-19). Enforced by constructing the `Date` from split parts, never from the ISO string (§7). |

Every case above has a defined behaviour. None is "TBD".

## 10. Example Scenarios

All against a freshly `reset()` store, server on `localhost:3000`, browser-local date **2026-08-01**.

### Scenario 1 — Normal: adding a task with a future deadline

**Input**
```
POST /tasks
Content-Type: application/json
{"title": "Renew passport", "due_date": "2026-08-05"}
```

**Expected output**
- Response `201`, body exactly:
  `{"id": 1, "title": "Renew passport", "completed": false, "due_date": "2026-08-05"}`
- Stored in `_tasks` as that same dict — `due_date` is the plain string `"2026-08-05"`, no time component.
- Client: `isOverdue` → `"2026-08-05" < "2026-08-01"` → **false**.
- The row renders inside `<ul id="task-list">`, showing `Renew passport` and `Due Wed 5 Aug 2026`, its date input pre-filled with `2026-08-05`.
- No `overdue` class, no `OVERDUE` badge, no red border. `#overdue-heading` and `#overdue-list` remain `hidden`.
- Nothing is sent anywhere — no email, no push, no notification of any kind.

### Scenario 2 — Alternative valid: backdating an existing task makes it late immediately

**Input**
```
POST  /tasks            {"title": "File tax return"}      -> id 1
POST  /tasks            {"title": "Reply to landlord"}    -> id 2
PATCH /tasks/2          {"due_date": "2026-07-31"}
PATCH /tasks/1          {"due_date": "2026-07-30"}
```

**Expected output**
- Both `PATCH`es return `200`. The last returns exactly:
  `{"id": 1, "title": "File tax return", "completed": false, "due_date": "2026-07-30"}`
- No warning, no confirmation dialogue — past dates are allowed (decision 8).
- `completed` is still `false` on both. Before A3, the same request would have returned `"completed": false` by coercion rather than by preservation — with a completed task it would have wrongly flipped it (F11, AC-5).
- Client: both are overdue. `#overdue-heading` becomes visible and `<ul id="overdue-list">` contains, top to bottom:
  1. `File tax return` — `OVERDUE`, `Due Thu 30 Jul 2026`
  2. `Reply to landlord` — `OVERDUE`, `Due Fri 31 Jul 2026`
  Earlier date first, so `id` 1 sorts above `id` 2 despite being patched second (AC-15).
- `<ul id="task-list">` is empty and takes no vertical space (EC-12 in the layout sense — only the Overdue section renders).

### Scenario 3 — Failure: a malformed date is rejected and nothing is written

**Input**
```
POST  /tasks   {"title": "Book dentist", "due_date": "05/08/2026"}
```

**Expected output**
- Response `400`, body exactly `{"error": "due_date must be a date in YYYY-MM-DD format"}`.
- `_next_id` is **not** incremented and no task is appended. A follow-up `GET /tasks` returns `[]`.
- Identical response and message for `{"due_date": "2026-02-30"}` (regex passes, `fromisoformat` rejects) and for `{"due_date": 20260805}` (not a string).
- Contrast `PATCH /tasks/99 {"due_date": "not-a-date"}` on a non-existent task: also `400`, **not** `404` — the body is validated before the lookup (AC-8). But `PATCH /tasks/99 {"due_date": "2026-08-05"}` returns `404 {"error": "task not found"}` (EC-18).

### Scenario 4 — Deliberate behaviour that looks like a bug: completing a task two days late

Included because this is the rule most likely to be "fixed" by an implementer who assumes late completions should be recorded.

**Input**
```
POST  /tasks    {"title": "File tax return", "due_date": "2026-07-30"}   -> id 1
(user ticks the checkbox in the browser on 2026-08-01)
PATCH /tasks/1  {"completed": true}
```

**Expected output**
- Response `200`, body exactly:
  `{"id": 1, "title": "File tax return", "completed": true, "due_date": "2026-07-30"}`
- **`due_date` is unchanged.** Nothing records that the task was completed two days late — there is no completion timestamp in the model and none is added (F5).
- After `fetchTasks()`: the row leaves `#overdue-list` and renders in `#task-list` at its ascending-`id` position with class `completed` — strikethrough title in `#888`, date text `Due Thu 30 Jul 2026` also struck through.
- **No** `OVERDUE` badge, **no** red border, **no** "completed 2 days late" text, **no** amber "was late" variant.
- It was the only overdue task, so `#overdue-heading` and `#overdue-list` both become `hidden` again (AC-18).
- This is decision 6 as given, not an oversight. **Do not add a late-completion marker.**
