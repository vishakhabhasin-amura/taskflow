# 4.1 Reference Requirement Agent Output (Python)

Hand this to the Implementation sub-team if the Requirement sub-team isn't done by Checkpoint 1.

## Acceptance criteria

1. `POST /tasks` accepts an optional `dueDate` field (ISO 8601 date string).
2. A task is considered overdue if `dueDate` is before the current server date, AND `completed`
   is false.
3. `GET /tasks` accepts an optional `?sort=dueDate` query parameter, returning tasks ordered by
   `dueDate` ascending.
4. Tasks with no `dueDate` are sorted to the end of the list.

## Assumptions made

- "Overdue" is evaluated at end-of-day granularity (date comparison, not timestamp), using
  server local time.
- Overdue is exposed as a computed field (`isOverdue: boolean`) in the API response rather than
  stored — it is always derived fresh.
- Completed tasks are never marked overdue, regardless of `dueDate`.

## Open questions flagged for a human

- Should users be able to edit a due date after task creation? (Out of scope per PRD non-goals,
  flagged for future iteration.)
- Should there be a grace-period buffer (e.g., a task due "today" is not overdue until
  tomorrow)? Assumed no buffer for now.

## Files likely affected

- `models/task.py` (accept `due_date` on create, add `is_overdue` computation)
- `routes/tasks.py` (accept `dueDate` on POST, support `?sort=dueDate`)
- `public/app.js` (display due date + overdue styling)

## Example scenarios

1. Task created with `dueDate=2026-07-20` (past), `completed=false` → `isOverdue: true`
2. Task created with `dueDate=2026-07-20` (past), `completed=true` → `isOverdue: false`
3. Task created with no `dueDate` → `isOverdue: false`, sorts last
